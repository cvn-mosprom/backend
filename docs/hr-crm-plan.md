# HR CRM: анкеты, достижения из игры, очки достижений — план и спринты

Дата: 24.10.2026. Бэкенд делаем мы (C1–C6), фронтенд — владелец фронта (F1–F6).

## Зачем

HR сейчас видит кандидатов только в Telegram-боте: карточка лида, кнопки статусов, `/leads`, `/export`. Игровой
профиль (что человек реально делал в цехе) почти не используется: в карточке есть лучшая профессия, место в сезоне
и счёт квиза, и всё. Цель — веб-CRM, где у каждого кандидата есть анкета и доказанный игрой профиль: достижения,
очки достижений, компетенции и соответствие вакансии. В ней HR ведёт воронку от отклика до найма.

## Что уже есть (основа)

- **Анкета.** Таблица `leads`: 18+, согласие и отзыв по 152-ФЗ, теги, статусы `new|contacted|interview|rejected|hired`,
  `hr_note`, outbox. HR-бот выдаёт карточки и кнопки статусов.
- **Игровые данные на сервере:**
  - `factories.state`: уровень, XP, ★, качество, коллекция SKU, навыки `speed/accuracy/attention/endurance`,
    `byProfession {played, wins, avgScore}`, диалоги туториала, факты музея, рефералы, `shiftsTotal`;
  - таблица `shifts`: каждая засчитанная смена с метриками;
  - `season_results`, `quiz_answers`, `events` (воронка).
- **Вход в веб через Telegram-бота** (S14): Bearer-сессии. Отдельной ролевой модели пока нет: HR — это список
  `HR_ADMIN_TG_IDS` в `.env`.

## Ключевые решения

1. **Достижения считает сервер.** В игре системы достижений нет, поэтому каталог живёт на бэкенде
   (`api/app/achievements/catalog.py`, версия каталога в коде). Достижения выводятся только из данных, которые
   сервер уже проверил: состояние цеха после sim, `shifts`, `season_results`, `quiz_answers`. Клиент не может прислать
   «я получил достижение».
2. **Очки достижений (ОД)** — сумма очков полученных достижений. Это игровая метрика: видна игроку, есть таб
   в топе. HR видит ОД рядом с **индексом компетенций** — шесть шкал 0–100: скорость, точность, внимательность,
   выносливость, надёжность, знание компании. Шкалы собираются из навыков, достижений и квиза по прозрачной формуле.
3. **Соответствие вакансии (fit)** считается правилом, а не ML. Для каждой профессии задан набор достижений и
   компетенций; результат 0–100 с объяснением, из чего он сложился. HR видит «почему 82», а не чёрный ящик.
4. **CRM — веб-раздел того же фронтенда** (`/hr/*` в SvelteKit, тот же origin и Caddy). Вход через бота (S14),
   роли на сервере. Бот остаётся для уведомлений и быстрых действий.
5. **ПДн и 152-ФЗ.** Отозвавшие согласие скрыты из CRM: остаётся только запись для аудита. Каждый просмотр
   карточки с ПДн пишется в журнал доступа. Экспорт доступен только ролям `hr_lead` и `admin`.

## Каталог достижений (стартовый, ~30 шт.)

У каждого достижения есть: `id`, название, описание, категория, уровень (бронза/серебро/золото), очки,
компетенция, которую оно подтверждает, признак «скрытое», признак «сезонное», прогресс (`current/target`).

| Категория | Примеры (очки) | Источник | Компетенция |
|---|---|---|---|
| Обучение | «Первая линия» — прошёл туториал (10); «Первый заказ» (10) | dialogs, collection | — |
| Производство | «1 000 / 10 000 / 100 000 бутылок» (10/25/50); «5 SKU / все SKU в коллекции» (20/50) | sim.produced, collection | надёжность |
| Качество | «Без брака» — качество ≥ 98 % на 1 000+ бутылок (30); «Контроль ОТК» — 10 заказов с minQuality ≥ 0,9 (25) | quality, orders | внимательность |
| Профессии | по каждой профессии: 5/25 смен (10/25), win-rate ≥ 70 % на 10+ сменах (30), avgScore ≥ 0,85 (40) | shifts, byProfession | по профессии |
| Скорость | «Реакция»: 10 смен с reaction_ms < 400 (25) | shifts.metrics | скорость |
| Выносливость | «Неделя на смене»: 7 дней подряд со сменой (30); «Все 5 смен за день» ×5 (20) | shifts | выносливость |
| Надёжность | «Точно в срок»: 10 заказов без просрочки (25); «Без долгов»: аванс погашен до срока (15) | orders, loan | надёжность |
| Знание компании | «Музей»: все факты (20); квиз 6/8 и 8/8 (20/40) | factsSeen, quiz_answers | знание компании |
| Сезон | топ-50 / топ-10 / топ-3 сезона (30/60/100) | season_results | — |
| Команда | «Наставник»: 3 приглашённых (20) | referrals | — |

Веса и пороги лежат в каталоге и правятся без миграций. При смене версии каталога полученные достижения не
отзываются.

## Архитектура данных (бэкенд)

- `achievements_earned` (user_id, achievement_id, season_id null, tier, points, earned_at, evidence jsonb,
  catalog_version; unique по (user_id, achievement_id, season_id)).
- `achievement_progress` (user_id, achievement_id, season_id, current, target, updated_at) — для прогресс-баров.
- `player_scores` (user_id, season_id, achievement_points, competency jsonb `{speed,…}`, fit jsonb
  `{operator: {score, reasons[]}}`, updated_at) — денормализовано для сортировки в CRM и топа.
- **Движок:** `evaluate(user)` — чистая функция, которая по данным пользователя возвращает достижения, прогресс,
  компетенции и fit. Запускается:
  - после каждой успешной игровой команды, в той же транзакции и только по дешёвым правилам из снимка;
  - после `submitShift`;
  - фоновым пересчётом из бота каждые 10 минут для правил, которым нужны запросы к `shifts`, `season_results`
    и квизу;
  - при закрытии сезона.
- **Новые достижения** попадают в ответ команды (`achievementsUnlocked: [{id, title, points, tier}]`) и в outbox
  (`achievement_unlocked`): игрок получает уведомление в боте (опционально), HR — в ленте кандидата.
- **CRM:**
  - `hr_users` (tg_id, role `hr|hr_lead|analyst|admin`, active) — замена `HR_ADMIN_TG_IDS`, с сидом из env;
  - `lead_events` — история кандидата: смена статуса, заметка, назначение, просмотр, экспорт;
  - `lead_notes`; `leads.assignee_id`, `leads.stage_changed_at`;
  - статусы расширяются до `new → screening → interview → offer → hired | rejected | reserve`, старые маппятся;
  - `vacancies` (id, profession_id, title, city, active, требования: компетенции и достижения).

## API (новое)

Игрок:
- `GET /api/achievements/me` — каталог с прогрессом, полученные достижения, ОД, компетенции.
- В ответах команд появляется поле `achievementsUnlocked`. В `GET /api/factory/{id}` и `season/summary` — ОД и
  топ-3 достижения.
- Новый таб лидерборда `achievements` (по ОД).

HR (`/api/hr/*`, Bearer-сессия плюс роль; все действия попадают в `lead_events`):
- `GET /api/hr/me` — роль и права.
- `GET /api/hr/candidates`: фильтры (статус, вакансия, вуз, курс, теги, ОД от–до, компетенция ≥, fit ≥, сезон,
  назначенный), сортировки (свежие, ОД, fit, место), курсорная пагинация.
- `GET /api/hr/candidates/{id}` — анкета, игровой профиль, достижения, компетенции, fit по вакансиям, история,
  заметки. Пишет событие «просмотр».
- `PATCH /api/hr/candidates/{id}` — статус, назначенный, теги. Есть проверка версии: два HR не затирают правки
  друг друга (409).
- `POST /api/hr/candidates/{id}/notes`; `GET /api/hr/pipeline` — канбан-счётчики и карточки по колонкам.
- `GET /api/hr/analytics` — воронка (события и статусы), источники, распределение ОД и компетенций,
  конверсия по вузам.
- `GET /api/hr/export.csv` (`hr_lead`+); CRUD `GET|POST|PATCH /api/hr/vacancies` (`hr_lead`+);
  `GET|POST|PATCH /api/hr/users` (`admin`).

## Решения (24.10, согласовано)

1. Статусы: `new → screening → interview → offer → hired | rejected | reserve`; старые `contacted` → `screening`.
2. Игроку в бот — только золотые и сезонные достижения (и только с включёнными уведомлениями); в игре тост на каждое.
3. Fit по вакансиям видит **только HR**. Игрок видит достижения, ОД и свои компетенции, но не fit.
4. HR пишет кандидату из CRM шаблонами (приглашение на интервью, оффер, отказ, свободный текст с правкой):
   `POST /api/hr/candidates/{id}/messages` → outbox → бот; только если кандидат запускал бота; всё в истории кандидата.
   Входит в C4 (бэкенд) и F4 (кнопка «Написать» в карточке).

Нумерация миграций: C1 — `0012`, C3 — `0013` (down `0012`), дальше по порядку.

**Адаптации к данным (чего в плане не было)**

1. **Профессии: по две записи на профессию** вместо четырёх (5 смен; «ас» сводит 25 смен, win-rate и средний балл в одно условие), иначе
   каталог вырос бы до 49. Пороги живут в `catalog.py`; добавить ступень = запись + рост `CATALOG_VERSION`.
2. **Заказы и аванс.** Сим убирает закрытый заказ через сутки после принятия, а погашенный аванс сразу, так что «сколько заказов
   выполнено» в состоянии не хранится. Движок ведёт монотонные счётчики в `achievement_progress` (id `_counters`, колонка `meta`:
   `any`, `done`, `otk`, `seen` — до 200 id учтённых заказов, `loan`, `loans_ok`); заказ учитывается один раз по id, сколько бы
   раз ни считали состояние. Просроченный заказ сим закрывает как `failed`, поэтому `done` всегда «в срок»; учебный заказ идёт только в
   `first_order`. Для игроков, которые были до C1, пересчёт видит лишь заказы, ещё лежащие в состоянии (около суток): `on_time_10`,
   `otk_control`, `no_debts` для них копятся с момента выката. «Без долгов» засчитывается, если счётчик видел аванс активным (его выдача
   — команда, хук её видит), потом аванс исчез, последний платёж `loanLog` с остатком 0 пришёл раньше `takenAt + 48 ч` и просрочка
   (`overdueApplied`) не фиксировалась.
3. **`byProfession` против таблицы `shifts`.** По каждой профессии берётся источник с большим числом смен (в проде они совпадают, но
   в dev-БД у 189 записанных смен старой сборки `byProfession` был пуст).
4. **«Все 5 смен за день ×5»** = 5 суток МСК, где принято не меньше `SHIFTS_PER_DAY = 5` смен; сутки — по `created_at` в МСК.
5. **Рефералы.** Бэкенд нигде не увеличивает `state.referrals` (это делает только мок), поэтому приглашённых считаем по
   `users.source = 'ref_<id игрока>'` (клиентский `refLink` кладёт `player.id` = `users.id`), без ботов, тестовых игроков и самого себя.
6. **Викторина**: банк теперь из 8 вопросов (S9), цели 6 и 8; считаются только id текущего банка.
7. **Сезонные места** берутся из замороженного `season_results.place` (место, как его видел игрок, с демо-ботами в рейтинге);
   сезонное достижение выдаётся отдельной строкой на каждый сезон и каждый раз даёт очки.
8. **Модель данных.** Вместо `season_id null` — `season_key int` (0 = не сезонное, иначе id сезона), чтобы уникальность `(user_id,
   achievement_id, season_key)` работала без NULL. Добавлено: в `achievements_earned` — `earned_season_id`, `granted_via`
   (`hook|shift|recompute|backfill`), `catalog_version`, `evidence`; в `achievement_progress` — `meta`; в `player_scores` —
   `season_points`, `evaluated_at` (+ `competency`/`fit` для C2). `achievement_points` — сумма очков всех полученных за всё время, на
   строке сезона фабрики; `season_points` — часть, полученная в этом сезоне. Выданное не отзывается, прогресс монотонен.

**Как это работает**

- **Хук 1** (`GameService.command`, в той же транзакции после записи состояния): дешёвые правила только по состоянию; два SQL
  (SAVEPOINT и один SELECT с блокировкой счётчиков), если ничего не изменилось; измерено ≈ 2,5–3 мс (Docker Desktop на Windows), сам
  движок 0,05 мс. Ошибка внутри хука откатывает только его SAVEPOINT: команда проходит. Боты и тестовые игроки пропускаются.
- **Хук 2**: после принятого `submitShift` (строка в `shifts` уже вставлена) добавляются правила по таблице смен.
- **Пересчёт** `POST /internal/achievements/recompute {limit 1..1000 (200), since?, after?, force?, dry_run?}` →
  `{evaluated, failed, granted, points, unlocked, remaining, next_after, ms}`: полный набор правил для игроков, у которых фабрика
  менялась после последнего полного пересчёта (`player_scores.evaluated_at`) или появились новый ответ викторины / итог сезона. Бот
  вызывает его задачей `achievements_recompute` каждые 10 минут, идя по `remaining`/`next_after` (до 20 вызовов за запуск).
  Правила по викторине, сезонам и приглашённым поэтому срабатывают с задержкой до 10 минут.
- **Разовый пересчёт**: `docker compose exec api python -m app.achievements.backfill [--batch 200] [--dry-run]` (`granted_via =
  backfill`, JSON-итог). На dev-БД: 1 509 игроков, выдано 114 достижений 49 игрокам (1 370 очков); повторный запуск выдаёт 0.
- **Для C2**: новые достижения команды лежат в `CommandBody.achievements_unlocked` (`[{id, title, description, category, tier,
  points, hidden, seasonal}]`), тело HTTP не менялось; `catalog.public_catalog()` и `Achievement.public()` — готовый каталог для
  `GET /api/achievements/me` (скрытые маскирует вызывающий). Outbox `achievement_unlocked` и уведомления — C2.

## C3 as built (роли и доступ HR)

Код: `api/app/hr/access.py` (зависимость, маскирование, журнал, сид), `api/app/routes/hr.py`, миграция `0013`
(`hr_users`, `lead_events`), бот: `bot/app/hr/access.py`. Тесты: `api/tests/test_c3_hr_access.py`, `bot/tests/test_c3_roles.py`.

**Вход.** Основной путь — Bearer-сессия веба (S14); `tma` и `dev` (при `DEV_AUTH=1`) работают так же, поэтому e2e и dev-инструменты
не требуют отдельной схемы. Без заголовка или с чужим токеном — 401; пользователь без активной строки в `hr_users` или с ролью ниже
нужной — 403 `forbidden`. Роль проверяется на каждом запросе: деактивация действует сразу, в том числе на живую сессию.

**Роли.** Порядок `analyst < hr < hr_lead < admin`; `hr_actor(min_role)` — нижняя граница в этом порядке. `analyst` — только чтение
без ПДн, `hr_actor("analyst")` = любая активная HR-роль, `hr_actor("hr")` = право писать.

| Право (`permissions[]` в `/api/hr/me`) | analyst | hr | hr_lead | admin |
|---|:-:|:-:|:-:|:-:|
| `candidates.read` — список, воронка, карточка | да | да | да | да |
| `candidates.pii` — ФИО, телефон, email, telegram, дата рождения, заметки HR | **маска** | да | да | да |
| `candidates.write` — статус, назначенный, теги, заметки, сообщения кандидату | нет | да | да | да |
| `analytics.read` | да | да | да | да |
| `vacancies.read` | да | да | да | да |
| `vacancies.write` | нет | нет | да | да |
| `export` — CSV | нет | нет | да | да |
| `users.manage` — `/api/hr/users` | нет | нет | нет | да |

**Аналитик и ПДн (решение).** Видит список кандидатов, карточку (игровой профиль, достижения, компетенции, fit, история) и
аналитику, но поля ПДн приходят замаскированными: `fullName` → «Кандидат #<id>», `phone/email/telegram/birthDate/hrNote/tgUsername`
→ `null`, плюс флаг `piiMasked: true` (у остальных ролей `false`). Помощники `mask_pii(item, actor)` / `mask_pii_many` (camelCase и
snake_case ключи, `extra=` для новых полей). Ручки C4/C5 обязаны пропускать каждый ответ с данными анкеты через них; свободный
текст (заметки, сообщения) аналитику не отдаётся. В боте аналитик получает только агрегаты (`/hr /funnel /sources /stats /top`),
но не `/leads`, `/lead`, кнопки статусов и не `/export`.

**Ручки.**

- `GET /api/hr/me` (любая активная роль) → `{tgId, name, role, permissions[]}`.
- `GET /api/hr/users` (admin) → `{items: [{id, tgId, userId, name, username, role, active, createdAt, createdBy}]}`; `name/username` из
  строки игрока (null, пока человек не заходил).
- `POST /api/hr/users` (admin) `{tgId, role}` → 201 пользователь; уже есть (в том числе деактивирован) → 409 `hr_user_exists`
  (вернуть доступ — через PATCH). `tgId` ≤ 0 или не число, неизвестная роль → 422.
- `PATCH /api/hr/users/{id}` (admin) `{role?, active?}` (хотя бы одно) → пользователь. Нельзя менять свою роль и деактивировать себя
  → 409 `hr_self_change` (повтор текущих значений — безвредный no-op). Всегда остаётся хотя бы один активный admin → 409
  `hr_last_admin`: активные admin-строки берутся под `FOR UPDATE` в порядке id, поэтому два админа, одновременно разжалующие друг
  друга, не могут оба выиграть (проигравший получает 403: его права уже сняты). Неизвестный id → 404 `hr_user_not_found`.
- Все `/api/hr/*`: лимит `hr` — 120/мин на пользователя; `Cache-Control: no-store` на любом ответе, включая ошибки и 429
  (`NoStoreMiddleware`). В CORS добавлен `PATCH` (dev-веб на другом origin).

**Сид.** При старте API (и лениво при первом HR-запросе, если БД тогда не отвечала) каждый id из `HR_ADMIN_TG_IDS` без строки в
`hr_users` добавляется активным `admin` (`created_by = null`, `user_id` — если игрок уже есть). Существующие строки не трогаются:
правки админа переживают перезапуск. Переменная теперь только bootstrap; в compose она передаётся и в `api`.

**Журнал `lead_events`.** `log_event(session, lead_id, actor, kind, payload)` пишет в транзакции вызывающего (откатывается вместе
с изменением), `record_event(sm, ...)` — в своей короткой; виды `view|status|assign|note|message|export|tag` проверяются в коде, а не
check-ограничением (новые виды без миграции); в `payload` только id, статусы и счётчики, не ПДн. Правило для C4: каждый просмотр карточки — событие `view`
(`{"masked": bool}` для аналитика), все изменения — в той же транзакции. Бот уже пишет `status` (с `from/to`, `via: "bot"`) и `view`
при `/lead`; события экспорта (нужен `lead_id`, пишется по строке на экспортированную анкету) остаются за C5.

**Бот.** Доступ читается напрямую из `hr_users` на каждую команду (активная строка, любая роль). Минимум по командам: агрегаты — любая
роль; `/leads /lead` и кнопки статусов — `hr`+; `/export` — `hr_lead`+. Если в таблице нет ни одной строки или она недоступна,
работает `HR_ADMIN_TG_IDS` (каждый id = `admin`); при непустой таблице env игнорируется. Карточки анкет (outbox) уходят в `HR_CHAT_ID`,
иначе всем активным `hr/hr_lead/admin` (аналитику — нет, в карточке ПДн); алерт 5xx — активным `admin`.
