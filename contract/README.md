# contract/

The client/server contract is **generated**, never hand-written. Source of truth:
`vendor/frontend/web/src/lib/api/types.ts` (union `Command`, 28 variants incl. `tick`; `GameSnapshot`; `CommandResult`).

```
types.ts ──ts-json-schema-generator──▶ contract/schema/{command,snapshot}.schema.json
                                         └─datamodel-code-generator─▶ api/app/contract/generated/{command,snapshot,__init__}.py
```

| Artefact | Notes |
|---|---|
| `contract/schema/command.schema.json` | root `$ref: Command`; `Command` is a `oneOf` of 28 named variants (`PlaceCommand`, `SubmitShiftCommand`, ...) with an OpenAPI-style `discriminator` on `type`; `tick.events` is a `SimEvent` union discriminated by `k` |
| `contract/schema/snapshot.schema.json` | root `$ref: GameSnapshot`; also holds `CommandResult` (+ every shared type) |
| `api/app/contract/generated/command.py` | pydantic v2: `Command` (`RootModel` over a union with `Field(discriminator="type")`), one class per variant, all `extra="forbid"` |
| `api/app/contract/generated/snapshot.py` | `GameSnapshot`, `CommandResult`, `Order`, `Factory`, ... (`extra="forbid"` on purpose: a new field in the sim output must come with a `types.ts` change and a regeneration) |
| `api/app/contract/generated/__init__.py` | re-exports + `COMMAND_TYPES` (frozen, declaration order) + `parse_command(raw) -> <Variant>Command` |

Every generated file starts with `# GENERATED by contract/generate — do not edit.`

Notes for consumers:

* Unknown `type` -> `pydantic.ValidationError` (`union_tag_invalid`); a missing required field or an unknown field -> `ValidationError`.
* `tick.from` is a Python keyword: the field is `from_` with alias `from`. Always `model_dump(by_alias=True)`; forward the *raw* request dict to the sim when you can.
* TS `number` is `float` in the models (`x: float`); `Rot` is `Literal[0,1,2,3]`, `Level` is `Literal[1,2,3]`.
* JSDoc is deliberately ignored by the generator (`jsDoc: none`), so comment edits in the frontend never cause drift.

## Usage

```sh
contract/generate.sh              # regenerate schema + python (first run: npm ci + creates contract/.venv)
contract/generate.sh --schema-only
contract/check.sh                 # regenerate into a temp dir and diff; exit 1 = drift (CI / pre-commit)
```

`check.sh` prints a unified diff and `contract drift detected: run contract/generate.sh and commit the result` on failure.
Run it after every submodule bump (`vendor/frontend`), in CI, or as a pre-commit hook:

```sh
printf '#!/bin/sh\nexec contract/check.sh\n' > .git/hooks/pre-commit && chmod +x .git/hooks/pre-commit
```

Pins: `package.json` / `package-lock.json` (ts-json-schema-generator 2.9.0, typescript 5.9.3), `requirements.txt`
(datamodel-code-generator 0.35.0, pydantic 2.12.3, black/isort pinned because they format the generated code).
`tsconfig.json` maps the frontend's `$lib/*` alias to `vendor/frontend/web/src/lib/*`; the vendor `web/tsconfig.json`
(extends the missing `.svelte-kit`) is not used. Type checking is skipped (`skipTypeCheck`): `three` and friends are not installed here and the data types do not need them.

Windows: shell scripts run in Git Bash (`sh contract/generate.sh`). To keep the executable bit in git:
`git update-index --chmod=+x contract/generate.sh contract/check.sh scripts/simcommit.sh`.

## Tests

```sh
cd contract
py -3.12 -m venv .venv && .venv/Scripts/python -m pip install -r requirements.txt   # or let generate.sh do it
.venv/Scripts/python -m pytest
```

* `tests/test_commands.py` — each of the 28 types parses from the realistic examples in `examples/commands.json` into the right
  variant and round-trips losslessly; the type list equals the spec list (27 + `tick`) and the regex-extracted `types.ts` union;
  unknown `type`, missing required field (every required field of every variant), unknown extra field, bad enum values all fail —
  checked against both pydantic and the JSON Schema.
* `tests/test_snapshot.py` — `examples/snapshot.json` (a full snapshot) validates against model and schema; missing/extra keys fail.
  **Live sim check** (skipped unless `SIM_URL` is set): validates a real `POST /v1/bootstrap` snapshot and threads one factory
  through every example command (`/v1/command`), validating each returned snapshot. This is the guard for the S1 merge:

  ```sh
  docker compose up -d sim && SIM_URL=http://127.0.0.1:58080 .venv/Scripts/python -m pytest
  ```
* `tests/test_generation.py` — headers/LF/sorted JSON, and `check.sh` reports "in sync".

`examples/commands.json` mirrors how the frontend builds commands (`lib/ui/build.svelte.ts`, `game.svelte.ts`,
`OrdersScreen.svelte`, `ShiftOverlay.svelte`, ...). When `Command` changes, add an example for the new variant or the tests fail on purpose.

## Fallback (spec risk 2)

Not needed: ts-json-schema-generator handled the real `Command` union (including the `SimEvent` union, mapped
`Partial<Record<SkuId, ...>>` types and the `$lib` alias) on the first try. If it ever breaks, the fallback from the spec is: keep the
discriminator and payload validators by hand, freeze the type list from `types.ts` (`COMMAND_TYPES`) and keep `test_commands.py` as the guard.
